# recpt1（http モードで常駐）

[stz2012/recpt1](https://github.com/stz2012/recpt1) を OpenIRD の機器に置き、http モード
（`recpt1 --http <port>`）で常駐させるアドオン。機器が TS サーバになり、LAN の別のホストから
チャンネルを指定して、受信した TS をそのまま受け取れる。

## 入るもの

| パス | 中身 |
|---|---|
| `/usr/bin/recpt1` | 上流のソースに [patches/](patches/) の修正を当てて静的リンクしたもの。libarib25 は入れていない |
| `/etc/init.d/S80recpt1` | 起動スクリプト。起動のたびにサーバを立て、サーバが落ちたら立て直す |

導入した時点でサーバが起動し、削除の前に止まる。

## 使う

クライアントは `GET /<チャンネル>[/<SID>]` を投げる。接続を切るまで TS が流れ続ける。

```
curl -o out.ts http://<機器>:12345/27       # 地上波の物理 27ch
```

- チャンネルと SID の書き方は recpt1 のコマンドラインと同じ（`recpt1 --help`）。
- 同時に受けられるのは 1 クライアント（チューナが 1 つ）。
- スクランブルは解除しない。放送されたままの TS が出る。
- 認証は無く、機器の全インターフェースで待ち受ける。

機器の上で `recpt1 --device /dev/irdvideo0 <チャンネル> <秒> <ファイル>` と打って録ることも
できる。チューナは 1 つなので、配信と同時には使えない。

## 設定

`/etc/default/recpt1` に書く（無ければ既定値）。このファイルはアドオンの一部ではないので、
アドオンを入れ替えても残る。

```
PORT=12345
DEVICE=/dev/irdvideo0
```

変えたら `/etc/init.d/S80recpt1 restart`。ポートは、同じ LAN の EPGStation（8888）や
Mirakurun（40772）と紛れないものにする。

## 操作とログ

```
/etc/init.d/S80recpt1 {start|stop|restart}
```

recpt1 の出力はシステムログに入る（`/var/log/messages`、タグ `recpt1`）。接続元・チャンネル・
C/N・エラーがここに出る。サーバを立て直したときも
`the server has ended; starting it again in 5 seconds` と残る。

`/var/log` は tmpfs なので、機器を再起動するとログは消える。落ちた原因を調べるなら、
再起動の前に取っておく。

## 見張り

サーバ（recpt1）は、いくつかのエラーで自分から終了する（接続を受け付けられない、録画を
始められない、など）。起動スクリプトは見張り役（`/bin/sh /etc/init.d/S80recpt1 watch`）を
常駐させ、サーバが終了したら 5 秒後に立て直す。

- 見張り役の pid は `/var/run/recpt1-watchdog.pid`。`stop` は見張り役を先に止めてから
  サーバを止める。
- ポートが塞がっていてサーバが立たないとき、`start` は `FAIL` を出すが、見張り役は残って
  5 秒ごとに立て直しを試みる。ポートが空けばそのまま立つ。

## 上流 recpt1 への修正

上流の `--http` は、何日も動き続けるサーバとしては不具合が多い。[patches/](patches/) で次を
直している（どれも上流の不具合の修正で、配信の中身には触れない）。

- [0001](patches/0001-http-close-the-connection-when-the-tuner-cannot-start.patch):
  選局できないとき（受からないチャンネル・デバイスを開けない・知らないチャンネル）、上流は接続を
  閉じずにクライアントを待たせていた。そのたびにファイル記述子が 1 つ漏れ、上限（1024）に
  達するとサーバごと終了する。選局できなければすぐ接続を閉じる。クライアントからは、
  `200 OK` の直後に接続が終わるように見える。
- [0002](patches/0002-keep-the-memory-of-a-long-running-server-bounded.patch):
  メモリを有限にする。上流のキューは最大 134MB まで伸び、POE-BR100-YB1（Linux が使える
  RAM は約 143MB）では OOM で殺されていた。
  - キューの上限を 16MB（地上波で約 8 秒分）にする。クライアントの受信が遅れても、
    これ以上は溜めない。
  - セッションの終わりにキューに残ったバッファを解放する。上流は、クライアントが途中で
    切るたびにそれを漏らしていた。
  - チューナが少しずつ返しても、16KB を満たしてからキューに入れる。
- [0003](patches/0003-http-keep-serving-after-a-bad-request-or-a-failed-accept.patch):
  1 つのクライアントの不具合で、サーバごと終了しないようにする。
  - 対象: `accept()` の失敗、リクエストを読む前のリセット、`GET /`（チャンネル無し）、
    256 バイトを超える行、最初の接続での SIGPIPE。
  - 選局できずに閉じるとき、読み残したリクエストを読んでから閉じる。リセット（RST）では
    なく、ふつうの終わり方になる。
- [0004](patches/0004-write-a-whole-buffer-at-a-time-to-the-output.patch):
  出力（http のクライアント）へは、バッファ 1 つ（16KB）をまとめて書く。上流は UDP 向けの
  1316 バイトずつ書いていた。YB1 では CPU を TS の取り出しと分け合うため、この細かい書き込みが
  効く。受信しながらの送信の上限が、2.38MB/秒から 2.89MB/秒に上がる（openird-6b の実測）。
  地上波の多重は約 2.06MB/秒。

- [0005](patches/0005-http-the-sid-belongs-to-one-request.patch):
  SID（`GET /<チャンネル>/<SID>`）を要求ごとに決め直す。上流では次の不具合があった。
  - SID を指定しない要求にも、前の要求の SID が残っていた。
  - その SID は前の要求の文字列の中を指していたので、次の要求で中身が化けた。
  - 受け付けられない SID で、確かめずに NULL を使って落ちた。
  - リクエストの文字列を、読み終えたブロックの外で使っていた（スコープ外）。
- [0006](patches/0006-do-not-use-the-freed-last-buffer-when-a-session-ends.patch):
  セッションの終わりに、上流は解放済みの最後のバッファをもう一度使っていた。SID 付きの
  セッションをクライアントが閉じると、それでサーバが落ちた（SB-TV06-WRIP で見つかった）。

キューが上限に達したとき（クライアントの受信が続けて遅いとき）は、上流のとおり、チューナからの
読み出しが待たされる。その間に届いた TS は、ドライバのリングが溢れた分だけ欠ける。欠けた分は
ドライバの数える取りこぼし（overrun）に出る。

## 知っておくこと

- 一度配信した recpt1 は、SIGTERM では終了しない（配信中の 1 本が終わるだけ）。起動スクリプトの
  `stop` は TERM のあとに KILL を送る。
- recpt1 は pid ファイルを書かない。起動スクリプトはコマンドライン
  （`/usr/bin/recpt1 --http …`）でサーバを見分けるので、手で始めた録画は `stop` に巻き込まれない。

## 版と pin

版は `<上流の版>-<commit の先頭 7 桁>-<アドオンの改訂>`（例 `1.2.0-77c7bce-4`）。取得する commit
と改訂番号は `build.sh` の先頭にある。

- 上流を上げるときは `RECPT1_COMMIT`（と `RECPT1_VERSION`）を変える。`patches/` が新しい
  上流に当たらなければ、ビルドが止まる（上流で直っていれば、そのパッチは外す）。
- すでに配った `.ird` と中身が変わるのに上流の commit が同じときは、`ADDON_REV` を上げる。
  `addon/`・`patches/`・`build.sh` を変えたときと、SDK の pin を上げて作り直したとき（バイナリに
  入るコンパイラの識別文字列が変わる）がこれに当たる。版が同じままだと、機器の
  `ird-addon install recpt1` は「導入済み」とみなして入れ替えない。
- `recpt1 --version` は `1.2.0 (stz2012 77c7bce2527e + addons-for-oird patches, without libarib25)`
  のように、上流の commit とパッチの有無を出す。

ビルドの手順と SDK の pin はリポジトリの [README](../README.md)。

## 確認したこと

`1.2.0-77c7bce-4`（2026-10-17）:

- 0005・0006 は、ホスト向けにビルドした同じソースで確かめた。サーバは AddressSanitizer 付き。
  比べる相手は 0001〜0004 のもの（`-3` 相当）。偽のチューナは、2 番組（SID 1024 と 1032）を
  持つ合成の TS を流す:
  - SID 付きのセッションをクライアントが閉じると、`-3` 相当は heap-use-after-free で終了する。
    `-4` は報告なしで続ける。
  - SID 付きの要求や、空白を含む不正な要求のあとの SID なしの要求で、`-3` 相当は前の SID の
    番組だけ（あるいは PAT だけ）を出す。`-4` は TS 全体を出す。
  - 存在しない SID・数字でない SID・受からないチャンネルと SID の組み合わせでも、`-4` は
    落ちない。`-4` は、スコープの検査も含めて AddressSanitizer の報告が無い。
- ほかは `-3` と同じ試験を通した（メモリ・落ちる経路・連番の検査・導入・起動スクリプト）。

**`1.2.0-77c7bce-4` は実機ではまだ確かめていない。**

`1.2.0-77c7bce-3`（2026-10-17）:

- ビルド・導入・起動スクリプトは、`-2` と同じ試験を通した（下の `-2` の項）。
- 上流 recpt1 の修正（0002・0003）は、ホスト向けにビルドした同じソースで確かめた。比べる
  相手は、0001 だけを当てたもの（`-2` 相当）。偽のチューナは、YB1 のドライバと同じく 1 回に
  1880 B ずつ、毎秒約 2MB を返す。
  - 受信の遅いクライアント（毎秒約 1.2MB）に 30 秒流したとき、サーバの RSS は `-2` 相当が
    2→19→40→49MB と増え続け、`-3` は 2→7→14→18MB で頭打ちになる。
  - 受信を途中で止めてから切る（RST）セッションを 6 回くり返すと、`-2` 相当は 1 回あたり
    約 8.5MB ずつ増え（10→52MB）、`-3` は 2MB のまま。
  - `GET /`・リクエストを送る前のリセット・`accept()` の失敗（EMFILE）で、`-2` 相当は
    サーバごと終了し、`-3` は受け付けを続ける。
  - 選局できないとき、`-2` 相当のクライアントは 200 のあと ECONNRESET を受け、`-3` では
    200 のあと普通に終わる。
  - 偽のチューナに連番のバイト列を出させ、クライアントが受け取った 8MB に欠けも重複も
    無いことを確かめた（0002 の「満たしてから入れる」と 0004 の「まとめて書く」の確認）。

`1.2.0-77c7bce-3` を実機（POE-BR100-YB1）で確かめた（2026-10-17）。試した OpenIRD は
rootfs が v26.10-rc4-13-geb4be45、カーネルは read() を px4_drv と同じにした版（OpenIRD
d9bc7c4）。試験は openird-6b・amatsukaze-encode-61・amatsukaze-encode-98 が行った:

- 入れ替えると、見張り役・サーバ・logger の 3 本が上がり、12345 で待ち受ける。
- `GET /`・受からないチャンネル・リクエスト前のリセットのどれでも、サーバの pid は変わらない。
  受からないチャンネルでは、curl に 200・0 バイトで普通に終わる（RST にならない）。
- 受信途中で切る（RST）セッションを 20 回くり返しても、サーバの VmRSS と機器の空きメモリ
  （約 91.6MB）は横ばい。
- 録画システム（Mirakurun の PX）と同じ局（T21）を 12 分同時に受けた:
  - 受信量は PX の 99.8%（10 秒ごとでも 98〜104%）で、送信は受信に追いついている。
  - CC エラー 0、PCR の飛び 0、ビットレートは PX と同じ 17.23Mbps。
  - ドライバの取りこぼし（torn・overrun）は増えない。
  - その間、VmRSS と空きメモリは横ばい。
- 再起動すると、見張り役・サーバ・logger が自動で上がる。

PX との差は、PMT に載っていない PID（0x0135）が YB1 には届かないことだけだった。これは
OpenIRD のドライバが PAT・PMT に載った PID だけを通すためで、recpt1 とは関係しない。

`1.2.0-77c7bce-2`（2026-10-17）:

- OpenIRD 26.10-rc3 の SDK（`emma3sep-mipseb-musl`）でビルドでき、作り直しても `.ird` の
  SHA256 が変わらない。中の `recpt1` は静的リンクの MIPS ビッグエンディアン。
- 機器に載っている `ird-addon` を、機器と同じ版・同じ設定の BusyBox で動かし、base の
  ツリーの写しへ導入できる。
- 起動スクリプトを同じ BusyBox の上で動かして確かめた。相手はホスト向けにビルドした recpt1
  （同じソースとパッチ。チューナの ioctl だけ差し替え）:
  - start・二重の start・配信・restart・postinstall と preremove。
  - 選局の失敗を 30 回続けても、サーバのファイル記述子が増えない。クライアントはすぐ放される。
  - サーバを KILL すると、5 秒後に見張り役が立て直す。
  - stop は、配信中でも、見張り役が立て直しを待っている間でも、両方を止めて何も残さない。
  - ポートが塞がっていると start は FAIL を出し、空いたら見張り役が立て直す。
  - 手で始めた録画は stop に巻き込まれない。
- 上流のままのビルドで、選局の失敗を続けると記述子が漏れ、上限でサーバごと終了して、以後は
  接続を拒否することを確かめた（上限を 32 に下げて再現）。

`1.2.0-77c7bce-1` は、導入・削除・起動スクリプト（見張り役の無いもの）を同じやり方で
確かめたうえで、録画システム（Mirakurun の番組表取得）から使われた。10/17 の未明に
接続できなくなっていた（応答の速さから、拒否とみられる）。機器のログは残っておらず、上の記述子の
漏れによる終了とみているが、確定はしていない。

`1.2.0-77c7bce-2` を実機（POE-BR100-YB1・OpenIRD v26.10-rc4-13-geb4be45）で確かめた
（2026-10-17）:

- `1.2.0-77c7bce-1` からの入れ替え（`ird-addon install <file> <sha256>`）。
- 見張り役・サーバ・logger の 3 本が上がり、12345 で待ち受ける。
- 受かるチャンネル（/27）で 10 秒あたり 14 MB 前後の TS が来る。
- 受からないチャンネルを 5 回投げても、サーバの記述子は 4 のまま。クライアントは 200・0 バイトで、
  約 3.4 秒で放される。
- サーバを KILL したときも、`GET /` で終了したときも、約 7 秒後に見張り役が立て直す。
- stop と start。
- 機器を再起動すると、見張り役とサーバが自動で上がる。

その後、`-2` には次の問題が残っていることが分かった。どちらも `-3` で直した。

- 録画システムから長く受信すると、OOM で殺される（1 つのセッションの中でも、VmRSS が毎秒
  約 2.5MB 増えた）。
- `GET /`（チャンネルの指定なし）でサーバごと終了する（見張り役が立て直す）。

## ライセンス

recpt1 は GPL-3.0（上流の `recpt1/COPYING`）。`.ird` には recpt1 のバイナリが入るので、配る
ときは対応するソースを示す。ソースは上流の pin した commit と [patches/](patches/) で、ビルドの手順はこの
`build.sh`。静的リンクしている libc は musl（MIT）。
